# FRONTIER — Execution Plan and Acceptance Criteria

> **Immutable milestone plan.** Do not edit this file to mark progress, reschedule tasks, or add discoveries. Log actual status, timestamps, blockers, and revisions of implementation choices in `Documentation.md`. Milestones may overlap; order by risk and remaining time. (Updated once, by explicit authorization, for Incident FR-0153; immutable again.) The target is **service version 2**.

## Success definition

The target is **version 2** (Incident FR-0153: exactly three undisclosed changes vs. the v1 examples). Submit by **20:00 Bogotá time**: (1) reachable Railway replacement, (2) evidence-backed behavioral specification, and (3) complete `experimentos.jsonl`. Prioritize exact behavior on unseen **reset-controlled sequences**; the hidden set contains 100 tests with 40/45/15 single/short/long-sequence distribution. Every step must match status and body and complete within 5 seconds. The replacement must be entirely independent of the original.

## M0 — Bootstrap and safety baseline

**Work:** Inspect the challenge README/examples and existing files; agree on repository structure, environment configuration, secured bearer tokens, per-token counters, rate limiter, query logging, and experiment sequence isolation. Configure FastAPI test client and minimal local run commands.

**Acceptance:** Per-request experimental logging in `experimentos.jsonl` (README schema: `id`, `seq`, `x_req`, `hipotesis`, `request`, `status`, `response`, optional `conclusion`) works with unique monotonic ids, reset-bounded `seq`, no secrets, and a request counter/rate limiter (≤10/s, ≤8,000/day per token, per-agent budget enforced, infra rate-limit responses excluded). Repository runs locally; fixed instructions are readable; missing files or secrets are reported rather than invented; no original request occurs without researcher approval; request counting includes resets.

## M0b — Backend infrastructure and FastAPI initialization

**Work:** Initialize the Python/FastAPI app (modular monolith, dataclasses, in-memory store behind a replaceable interface), env-based config, and local run/test commands.

**Acceptance:** App starts locally; `/health` returns 200; `/__reset` reinitializes state; tests run with one command; no import path or network route to the original.

## M1 — First executable replacement

**Work:** Implement a minimal modular FastAPI service with routes, reset behavior, initial state store based on classes/dataclasses and dictionaries, command-dispatch skeleton, and deterministic response helpers. Put the storage behind a narrow interface.

**Acceptance:** `/health`, `/__reset`, and `/msg` are reachable locally; reset reconstructs an empty baseline; the known sample sequence can run as a historical v1 fixture even if not all responses agree; the production import graph makes **no** calls to the original.

## M1b — Version-aware golden regression framework

**Work:** Build offline tooling that converts log entries into stateful golden fixtures (version- and provenance-tagged), keeps historical v1 (the 20 examples) separate from the current v2 suite, replays sequences against the local FastAPI app (not the original), compares exactly per README rules, and reports metrics.

**Acceptance:** Every eligible v2 observation is represented in the golden suite and replays locally without calling the original API; sequences keep order from reset; successes and error responses are both covered; v1/v2 are never mixed in the current suite; recorded expectations are never modified; each run reports Request/Sequence Agreement Rates, totals, passing/failing sequences, earliest failing step with expected vs. actual, new regressions and known mismatches.

## M2 — Evidence-driven protocol and rule discovery

**Work:** Have the Proposer present prioritized, competing hypotheses; the researcher chooses one and sets a budget; the Experimental Agent tests it autonomously within the approved scope. Investigate protocol/auth/routes, control field, arity/casing/coercion, command results, errors, and error-precedence interactions. Capture every original request in `experimentos.jsonl`.

**Acceptance (initial behavior discovery):** Each investigated hypothesis is version-tagged and has an evidence trail and an explicit confidence level; all consumed requests (including reset) are accounted for; no unsupported rule is marked `confirmado`; no new hypothesis begins without approval.

## M3 — Stateful command equivalence

**Work:** Model account and operation life cycles, ID counters, balances, transfers, cancellation and reversal semantics, repeated calls, errors, and state/reset effects. Preserve quirks exactly; add regression tests for each observation.

**Acceptance:** Locally reproduce v2-verified observed sequences from a fresh reset as far as evidenced (the 20 v1 examples serve only as a historical reference; differences from v2 are reported, not hidden); no regression on previously passing observations; state invariants and unknown corner cases are distinguished from hypotheses.

## M3b — Version 2 implementation

**Work:** Implement version 2 as the primary target (no prior v1 build), using v2-verified evidence; v1-only evidence and unverified rules are marked `supuesto`.

**Acceptance:** All accumulated v2 golden tests run after every backend modification and remaining mismatches are explicitly reported; no newly introduced regression is left unreported; historical v1 expectations are not enforced as current.

## M4 — Differential verification and generalization

**Work:** Develop custom scripts for paired original/replacement sequences, trace comparison, adaptive adversarial cases, and controlled fuzzing. Test short and longer state-dependent sequences. Classify mismatches and iterate on the most important gaps.

**Acceptance (continuous differential verification):** The full golden suite runs after every backend change with metrics reported; comparisons are reproducible and include status and exact body semantics; mismatch artifacts identify input sequence and observed evidence IDs; tests contain both happy paths and adversarial cases; latency and budget are measured.

## M4b — Discovery and documentation of the three FR-0153 changes

**Work:** Through approved, budgeted, version-aware hypotheses, discover exactly the three changed behaviors, separating independent changes from consequences of one rule; document each and implement it.

**Acceptance:** Each claimed change records v1 behavior, v2 behavior, experiment IDs, confidence, and replacement implications; claims are backed by v2 evidence in `experimentos.jsonl` (not inferred from v1 alone); each has golden regression coverage; the count is evidence-based (three independent changes, none invented); the changes appear in the specification's `Cambios durante el día` and are ready for the technical debrief.

## M5 — Incident and evolving behavior

**Work:** Keep an original-query reserve. After a suspected or announced service change, use a small authorized sentinel suite to establish before/after differences, isolate changed behavior, and update implementation, regression suite, research memory, and the specification's `Cambios durante el día` section.

**Acceptance:** Any claimed change cites both prior and new observations, is distinguishable from infrastructure throttling, and has a regression test. No unnecessary SQLite migration: switch storage only if evidence or deployment constraints justify it.

## M6 — Deployment to Railway and submission hardening

**Work:** Deploy to Railway; configure auth/token securely; test public endpoints, unmatched routes and methods, reset determinism, malformed bodies, status/body fidelity, and response time. Where permitted, submit/validate the entrypoint and inspect aggregate feedback. Write and cross-check the seven-section specification; validate the `experimentos.jsonl` schema and evidence IDs.

**Acceptance:** The full golden v2 suite passes (or remaining mismatches are explicitly listed) against the deployed instance as well as locally. Public replacement is healthy, authenticated, stateful, resettable, and independent of the original; the URL is ready before the deadline; artifacts are complete, internally consistent and submitted on time. Leave safety margin for a final clean restart and sanity checks.

## M7 — Final conformance testing and technical debrief

**Work:** Final full golden regression (local and deployed), evaluation-shaped runs (reset per test; 40 single, 45 of 2–5, 15 of 6–12 steps; <5 s per step), a final v2 sentinel check if budget permits, and preparation of the debrief on incident FR-0153.

**Acceptance:** Final metrics and unresolved mismatches are reported in `Documentation.md`; expected outputs were never altered; the deployed replacement matches the latest observed v2 behavior and makes no original calls; the debrief explains all three changes with experiment IDs; specification, log, and deployed entrypoint are consistent and submitted before 20:00 Bogotá.

## Ongoing constraints and priority order

- **Accuracy over coverage claims:** an explicit `supuesto` is better than a false `confirmado`.
- **Research discipline:** approve one hypothesis, set an agent-specific cap, execute/log, then hand off and ask for the next approval.
- **Version discipline:** v2 is the target; v1 data is historical; never rewrite recorded expectations; run golden regression after every backend change.
- **Separation of concerns:** only offline research scripts query the original; the deployed replacement never does.
- **Time-aware execution:** obtain a functioning baseline and deployment path early; don't defer testing, evidence logging, or documentation to the end.
- **Durable memory:** summarize evidence, counterexamples, uncertainty, and the next action in `Documentation.md` after each meaningful milestone or agent handoff.

## Final release checklist (record results in `Documentation.md`, not here)

- Public Railway URL available; authenticated `/health`, `/__reset`, `/msg` tested.
- Other methods/routes and malformed requests handled as observed.
- State transitions and reset verified; no original-service dependency in runtime.
- Exact response matching and per-step <5 s checked.
- Original experiment log complete; `x_req` captured where returned; IDs unique.
- Specification contains all seven sections, evidence references, confidence labels, error precedence and change/risk notes.
- Recent change probes performed (if budget permits) and final behavior reflected.
- All submission links/artifacts delivered before 20:00 Bogotá time.
